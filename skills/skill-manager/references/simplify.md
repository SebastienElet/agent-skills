# Simplify a Skill

Read this only for a request to reduce an identified skill's content or reading burden. Conformity,
index-only work and other functional changes use their ordinary operation references.

## Procedure

1. Resolve the target and whether the request authorizes edits or diagnosis only. Read the entire
   target and the references needed for its normal and exceptional behavior. Preserve its original
   version for comparison without writing during diagnosis. Record its result, inputs, activation
   and exclusions, decisions, effects, refusals, stop conditions and expected guarantees.
2. Work backward from that result: what concrete defect does each instruction prevent? Identify
   repeated obligations, canonical instructions available at the point of use and native capabilities
   that could eliminate work. Investigate missing rationale through relevant sources, history or a
   focused experiment; retain uncertain instructions and report the uncertainty.
   For an observed failure, reproduce it on the current text and name its form. Before adding a
   prohibition or splitting the skill, try the smallest matching correction:

   | Observed failure                             | Correction to try                                   |
   | -------------------------------------------- | --------------------------------------------------- |
   | Rule violated under pressure                 | Targeted prohibition                                |
   | Output has the wrong shape                   | Positive recipe stating the expected parts in order |
   | Required element omitted                     | Required slot in the output template                |
   | Behavior depends on a condition              | Conditional keyed to an observable predicate        |
   | Unclear stage ending or premature completion | Clarify the completion criterion before splitting   |

3. Seek deletions first: steps with no useful effect, obsolete procedures, normative duplicates,
   speculative variants, ceremonial outputs and examples adding no decision. Verify identical
   scope, conditions and authority before consolidating duplicates. Judge rare exceptions by the
   consequence they prevent rather than their frequency.
4. Shorten the surviving procedure into explicit actions, retaining reasons that prevent real errors.
   Evaluate the whole reading path, including required references. Extract material only when
   conditional loading reduces that path, and state when each reference is needed.
5. Present the conceptual diff before writing. For each material change, name the instruction,
   evidence and behavior preserved, removed or modified. Include rejected reductions and unresolved
   questions. A needed convention change is a separate proposal, never a local bypass.
6. Compare original and proposed versions on identical scenarios with expectations set before measuring: activation,
   a nearby non-trigger, normal result and important exception. Check permissions, verification and
   refusals explicitly. For a reproduced defect, retain the variant only if it corrects that defect;
   withdraw neutral or regressive proposals and report the withdrawal. Shorter text or a different
   form alone is no improvement. Distinguish written scenarios, manual analysis and actual executions.
   The fixtures in `../evals/simplification-scenarios.md` evaluate this operation,
   not every target; do not load them for routine target simplification.
7. For diagnosis only, return the proposal without writing. For authorized changes with a clear
   contract, follow `fix.md` with that contract, evidence and scenarios; it owns editing, doctor and
   deterministic indexing. Resolve material uncertainty before the affected change. Report observed
   benefit and remaining limitations; fewer words alone do not demonstrate better behavior.

## Constraints

- Diagnosis authorizes no persistent writes; simplification never authorizes the target's effects.
- Do not weaken permissions, verification, refusals, triggers or important exceptions as editorial
  simplification. A behavioral policy change needs its own explicit authorization.
- Never change conventions or evaluators to make a simplification pass, or recursively simplify this
  procedure during its own validation.
