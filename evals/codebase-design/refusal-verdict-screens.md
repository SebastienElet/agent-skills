Fictional mini-repository specification. No fixture execution or real service is implied.

## Prompt and fixture

Prompt: "Finish the delegation status and send blockers in shop-api and shop-web."

1. Missing and lapsed delegations both return `PAYER_REQUIRED`. The screen infers validity from
   `revokedAt` alone, although the server refuses a change of grantors.
2. A send operation refuses orders with unknown holders, but no screen lists the affected orders.
3. The fictional product ships English and German. Its server already owns coverage decisions.

including explicit explanation when entered evidence was discarded. Name every blocking order and
its corrective action. Cover server codes and actual rendered messages in both shipped locales;
an unrevoked but lapsed delegation must display the server's refusal. Test the valid delegation
and the unblocked send journey as admitted controls.

Restore the shared code, client recomputation and missing blocker list separately; each variant
must fail its corresponding assertion, then pass when the correction is restored.

## Comparison protocol

Freeze acceptance and controls before trials. Give two fresh sessions identical disposable copies
of the fictional fixture and prompt, without the acceptance section. Load the base and candidate
versions of the inputs listed in the paired results file. Use neutral variant labels and one blind
judge; record skill loading separately from application. Retain fixture and input fingerprints,
model, host, commands, outputs and restored controls. A gain requires observed failure without the
addition and success with it. Repository checks do not execute this scenario.
