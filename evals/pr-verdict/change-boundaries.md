# Changed boundary scenarios

All repositories, names, versions and artifacts in these cases are invented. These are decision
scenarios, not executable applications or evidence that their represented commands ran.

## Protocol

Give a fresh evaluator the selected skill snapshot and these scenarios, without expected answers
or earlier conclusions. For each case, report whether readiness or the stated guarantee is supported,
the precise mechanism or evidence gap, and the smallest relevant next check or correction. Do not
edit files, run represented commands, access a forge or publish. Use identical scenarios for both
wordings. Record input fingerprints and actual execution limits separately from the decisions.

The fixed criterion is correct treatment of every supplied violation without rejecting the safe
controls or inventing runtime observations. One run per wording can expose a missed decision; it
cannot establish a reliable improvement rate, host activation or implementation correctness.

## Cases

1. **Integrated consumer.** A branch makes `createHost({ auditSink })` mandatory and updates its
   consumers. The destination then adds a consumer calling `createHost({})`. A conflict-free merge
   preview and branch CI are supplied; the destination is not integrated. The author calls the PR
   ready. Which tree and consumers need checking, and what belongs in the delivery evidence?
2. **Colliding identifiers.** The local branch adds decision number `0082`, a migration dated before
   the newest destination migration, and manifest version `8` for one permission set. An open PR
   already uses `0082` and version `8` for another set. A second decision document on the destination
   also uses `0082`. No textual merge conflict occurs. What must be compared and when rechecked?
3. **Permissive routing.** An authenticated-only global guard allows undeclared permissions. A new
   export route has no permission; an existing note-writing route in the same module has no access
   scope check. All supplied tests use an administrator. What inventory and refusal cases are needed?
4. **Non-discriminating tests.** A tenant test gives the foreign subject an empty resource scope.
   A redaction test uses a partial object match on stored data. An in-memory adapter creates active
   objects, while the real adapter creates drafts. All tests pass. Which claims remain unsupported,
   and how would a red witness discriminate the intended behavior?
5. **Cached or skipped guard.** A scanner reads hidden YAML directories, but its cache key covers
   only visible `.yml` files. Its regex recognizes one forbidden flag spelling and joins fragments
   from separate shell commands. CI can return success after a planning-only invocation, early exit,
   duplicate script key or decoy step. The PR claims all reintroductions are refused. Assess the
   claim and propose bounded evidence without expanding a declaration mirror gate.
6. **Repeated state change.** Cancellation issues a second credit when replayed. Only the first
   workflow action checks an expected version; later edits do not. Creation accepts zero although
   finalization requires a positive amount. A successful form keeps its old version. Multiple source
   addresses select the first; a shared amount is counted in full for each holder. Identify the
   failed boundaries and observable refusal or allocation checks.
7. **Personal copies.** An idempotency store retains a response containing a personal label and
   email without purge. Export/erasure uses a handwritten context list predating a new personal
   reference on the destination. Reads expose an unused email; aggregates include anonymized rows
   contrary to contract. A versioned deletion endpoint changes success to blanket refusal without
   an approved contract amendment. What must be checked before delivery?
8. **Dependency installation.** An update contradicts the reason attached to an override, orphans
   a version-bound patch and resolves another package to an unapproved branch prerelease. Unit
   tests pass. An image installs from only some workspace manifests; no image build or startup ran.
   Is the upgrade qualified, and which evidence is missing?
9. **Supervisor completion.** A second termination signal interrupts cleanup; a child ignores
   termination; a worker wait has no deadline. Cleanup failure leaves exit zero and a success receipt.
   A subprocess returns zero with an output-buffer error. Which offline cases and status rules apply,
   and which process-containment limits must remain explicit?
10. **Commit scope.** A focused repair contains unrelated environment changes, a temporary `wip`
    subject and a verification-tooling rewrite without a coupling rationale. Two other commits are
    coherent subtasks of the promised fix. What should be separated or disclosed, and what may stay?
11. **Moved evidence.** After a push the description still presents the previous head's tests as
    current, omits commands/statuses/environment and cites green CI for a different synthetic merge
    tree. A proposed custom merge title removes the branch marker consumed by a required control.
    What needs refreshing in the push step, and can retained observations ever be reused?

## Safe controls

1. The destination is integrated; the recorded head/base, commands, statuses, environment and logs
   cover its new consumers and conflict resolutions. Identifier values were compared with destination
   and open PR heads. Coherent subtasks share one PR, with coupled verification changes explained.
2. A documented public endpoint intentionally permits anonymous access. Protected neighbors declare
   permission/scope and have minimally privileged allowed/refused cases with observed predicate-red
   failures. Exact storage assertions and shared real/double adapter contracts pass.
3. A scoped guard claims only its exercised forms, rejects inconclusive input and has a permitted
   control. Native task inspection shows every scanned input invalidates cache; logs and a failing
   witness establish actual CI execution. No new mirror gate is proposed.
4. Every action checks its expected version atomically; replay returns the prior result without a
   second effect. Inputs satisfy downstream domain restrictions; ambiguity remains explicit and
   allocations conserve totals. Personal copies have justified retention and exercised erasure;
   the published API contract is preserved.
5. Retained observations keep their original head/base and provenance, with a documented comparison
   of unchanged relevant inputs; required remote CI actually tests the current candidate. Approved
   prereleases, verified patches and successful image builds/startups are supplied. Supervisor tests
   cover deadlines, repeated signals, output errors and cleanup status while naming uncatchable-kill
   and detached-descendant limits. Do not invent missing evidence from facts already supplied.
